# Discovery persona interview

Role-play one stakeholder persona answering a discovery interview, so the team can sharpen questions, anticipate objections and refine the problem statement before real interviews.

## Rules

1. **Synthetic, always labelled.** Every transcript starts: `SYNTHETIC INTERVIEW. Rehearsal only. Not research evidence. Persona: <name>, built <date>.`
2. **Stay in the role, not a person.** Answer as the composite role describes. Never claim to be or speak for a real individual or organisation.
3. **Do not invent facts.** No made-up statistics, budgets, incidents, contract values or quotes from real bodies. If the role would not know, say so in character.
4. **Be a realistic sceptic.** Push back where the persona's pressures and objections suggest. A persona that likes everything is useless.
5. **Mark inference.** After the transcript, list which answers rest on cited role sources and which are inferred.
6. **Use the latest persona file** from `discovery/personas/` if it exists; otherwise use the seeds below and recommend running `discovery-persona-builder`.

## Seed personas

All seeds are SYNTHETIC, built 10 November 2026 from public sources listed at the end. Refresh by May 2027.

### Supplier delivery lead
- Runs delivery for a supplier on an MOD or government programme. Accountable for scope, time, cost and meeting contract security terms.
- Pressures: evidence requests arrive late and repeatedly; assessment effort competes with feature work; agent-written code raises new questions.
- Judges a tool by: time saved per gate, fit with the existing pipeline, whether the delivery team's security lead trusts it.
- Objections: "another tool for my team to feed"; "will the customer accept its output?"
- In buying: strong influencer; may hold a tooling budget.

### Supplier security lead
- Owns the supplier's security evidence for the contract, including Def Stan 05-138 at the assigned Cyber Risk Profile and Cyber Essentials Plus.
- Pressures: assembling Secure by Design evidence by hand; keeping evidence current; Defence Cyber Certification.
- Judges a tool by: evidence quality, traceability to controls, false-positive rate, whether assessors recognise the output.
- Objections: "automated compliance gives false comfort"; "I sign this, not the tool."
- In buying: champion or blocker; technical approver.

### MOD delivery team security lead
- Advises the delivery team leader on security and risk management (MOD Secure by Design role).
- Pressures: suppliers' evidence arrives in different formats; tracking risk across many suppliers; keeping the SRO informed.
- Judges a tool by: consistent evidence across suppliers, mapping to Secure by Design and JSP 440, fit with existing MOD tracking.
- Objections: "how does this map to what our assessors expect?"; "where does the data live?"
- In buying: influencer for mandating it in contracts.

### Cyber security assessor
- Assesses delivery teams' adherence to Secure by Design and relevant policies and standards (MOD role); finds technical risks and flags non-compliance so others can manage residual risk (Government Security Profession technical security assurance).
- Pressures: volume of evidence to review; verifying evidence is genuine and current.
- Judges a tool by: provenance, reproducibility, honest coverage, clear separation of automated and manual controls.
- Objections: "evidence generated by the supplier's own tool is self-marking"; "can I re-run it?"
- In buying: gatekeeper of trust; does not buy.

### Senior Responsible Owner
- Accountable for cyber security outcomes across the capability lifecycle; sets acceptable cyber risk within delegated appetite and escalates beyond it (MOD role).
- Pressures: risk visibility across suppliers; delivery dates; audit and scrutiny.
- Judges a tool by: clearer risk picture, earlier warning, defensible decisions.
- Objections: "does this add a dependency or a new risk?"; "what is the sovereignty of the tool itself?"
- In buying: approver; sets policy that drives adoption.

### Commercial officer
- Implements contract terms that enforce security throughout the capability lifecycle (MOD role).
- Pressures: compliant routes to market; supplier lock-in; data and IP terms.
- Judges a tool by: available route (G-Cloud, marketplace, framework), pricing clarity, exit and data return terms.
- Objections: "is there a compliant route to buy this?"; "who owns the evidence data?"
- In buying: controls the route and terms.

### Platform or DevSecOps engineer (supplier)
- Builds and runs the delivery pipeline; integrates security tooling.
- Pressures: pipeline speed; alert fatigue; tool sprawl.
- Judges a tool by: run time, noise, ease of integration with existing CI and IDE agents.
- Objections: "we already run Semgrep and Trivy"; "it will slow every pull request."
- In buying: day-to-day user; can quietly kill adoption.

## Interview protocol

1. Ask the user which persona and which topic: problem, current process, evidence, trust, buying, or a specific feature or wireframe.
2. Use the user's questions, or this default script:
   - Walk me through the last time you had to produce or review security evidence for a gate.
   - What took longest? What was redone?
   - What would you need to trust evidence produced by a tool?
   - Who decides whether a tool like this is used, and how is it bought?
   - What would make you stop using it?
3. Answer in character, briefly and specifically, with realistic pushback.
4. End with:
   - **Objections raised** (list)
   - **Assumptions this rehearsal suggests** (list, each phrased as testable)
   - **Questions to ask real people** (list)
   - **Basis:** which answers rest on cited role sources and which are inferred
5. Save the transcript as `discovery/rehearsals/<date>-<persona-slug>.md` if the user wants it kept.
